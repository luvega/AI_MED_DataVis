# 第2章 AI 生产力工具链与项目环境

## 本章定位

本章是第一篇“课程入口、工具链与 AI 协作规范”的第二章，承接第 1 章的课程定位，转入真实项目现场。它不把重点放在逐步安装教程，而是帮助学生理解：医药数据课程中的 AI 工作台由哪些工具组成，为什么要先确认目录、规则和输出位置，以及怎样留下可复查的环境验收和 AI 协作记录。

本章服务 36 学时课程中“AI 前置”的安排。课程大纲要求第 1-2 周建立 AI 使用边界、文件组织、命名规范、结果留痕、Prompt 记录和复现基础。因此，本章应把 Opencode、VS Code、终端、Git、Node.js、Miniconda、Pandoc 和 Skills 组织成一套“可协作、可核验、可回退”的项目环境，而不是软件清单。

本章不提前讲复杂编程、统计推断或组学分析。Python、R、统计模型、组学流程和医学解释将在后续章节展开。本章只要求学生能打开正确项目、读懂规则文件、确认当前路径、运行基础验收命令、区分原始材料和输出目录，并说明 AI 在本课程中的协助边界。

## 内容要点讨论结论

| 讨论点 | 采用方案 | 理由与边界 |
|---|---|---|

| 是否强调具体软件版本 | 不固定长期版本，只要求学生记录本机检查结果 | 工具、模型和插件会更新；课堂以教师发布说明为准 |
| 是否把 AI 作为自动分析者 | 不采用；AI 作为协作工具，学生负责核验和解释 | 课程大纲强调 AI 辅助而不替代思考 |
| 是否纳入 Git | 纳入，但只讲变更记录、审阅、回退和交接 | 不在本章展开分支、PR 或 CI |

| 本章学习证据 | 工具角色表、路径记录、环境验收表、项目目录图、AI 协作记录 | 这些产物能被教师和同伴复查 |

## 小节目录

### 2.1 本地 AI 工作台的基本组成

内容要点：

- 解释“本地 AI 工作台”不是单一聊天工具，而是由编辑器、终端、AI 助手和底层运行环境共同组成。
- 说明 Opencode、VS Code、终端、Git、Node.js、Miniconda、Python、Pandoc 和 Skills 在课程中的角色。
- 区分“会安装”和“会在项目中使用”：学生应能说清每个工具服务什么学习产物。
- 建立本章第一条主张：工具链的目标是让课程项目可读、可写、可核验、可交接。
- 学习证据：完成一张“工具-用途-验收方式-课程产物”对照表。

写作边界：

- 不比较不同 AI 模型优劣。
- 不固定某个版本号为长期要求。
- 不要求学生本章掌握复杂命令行操作。

### 2.2 Opencode、VS Code 与终端协作

内容要点：

- 说明 VS Code 负责显示和编辑项目文件，终端负责执行命令，Opencode 在终端中协助读文件、写草稿、解释报错和运行检查。
- 强调启动 Opencode 前必须确认当前路径。路径错误会导致 AI 读错材料或把输出写到错误位置。
- 引入常用基础动作：用 VS Code 打开课程项目文件夹，打开内置终端，运行 `pwd` 或 `Get-Location`，启动 `opencode`，查看 `/skills`。
- 讨论 Plan / Build 或“先分析再执行”的工作顺序：先让 AI 读规则和材料，说明任务边界，再写文件。
- 学习证据：提交当前项目路径记录、一次 Opencode 启动记录和一段“先读规则再行动”的提示词。

写作边界：

- 不展开全部快捷键。
- 不把 Opencode 输出当作已经核验的事实。
- 不建议学生在未确认路径时让 AI 写文件。

### 2.3 Git、Node.js、Miniconda 与 Pandoc

内容要点：

- Git：用于记录、审阅、回退和交接改动。重点讲 AI 协作中为什么更早需要版本控制。
- Node.js 与 npm：说明其作为部分命令行 AI 工具运行和安装基础的角色，不讲 JavaScript 编程。
- Miniconda 与 Python：说明其用于后续数据读取、清洗、统计和可视化脚本，不在本章讲包管理细节。
- Pandoc：说明其用于 Markdown、Word、PDF 或 HTML 等文档格式转换，转换后仍需人工检查格式和内容。
- 给出基础验收命令，如 `git --version`、`node --version`、`npm --version`、`conda --version`、`python --version`、`pandoc --version`。
- 学习证据：完成环境验收表，记录命令、输出摘要、状态和备注。

写作边界：

- 不要求本章初始化所有仓库。
- 不深入讲 GitHub 协作、分支或远程仓库。
- 不把 Pandoc 转换成功写成文档已经合格。

### 2.4 Skills 的安装、调用与课程使用边界

内容要点：

- 定义 Skill：一套可复用的 AI 工作规则，适合触发场景稳定、处理步骤可复用、输出标准明确的任务。
- 说明最小 Skill 由 `SKILL.md` 定义；`description` 决定触发质量，正文规定执行步骤，`scripts/`、`references/`、`assets/` 可作为增强层。
- 介绍渐进式披露思想：系统先看名称和描述，相关时再读取正文和附加资源。
- 给出课程适用场景：整理 AI 协作记录、检查图表契约、润色图注、生成课堂任务单、审阅证据边界。
- 强调课程边界：Skill 不能自动生成无来源医学结论；涉及药学、统计、组学或临床解释时，材料不足写 `需补证据` 或 `需人工确认`。
- 学习证据：写出一个“何时使用某个 Skill、何时不用”的判断表。

写作边界：

- 不要求学生本章编写复杂 Skill。
- 不把 Skill 写成万能提示词。
- 不让 Skill 代替人工核验、伦理判断或医学解释。

### 2.5 课程项目目录、规则文件与输出约定

内容要点：

- 说明目录是 AI 协作边界系统：让学生和 AI 都知道读什么、写什么、查什么、暂存什么。
- 固定本项目目录约定：`参考资料/` 只读，`大纲.md` 是教材结构唯一来源，`syllabus/` 放课程大纲，`chapters/chapter-{n}/本章大纲.md` 放章节工作区，`outputs/` 放本轮产出，`references/` 放模板和术语表。
- 说明规则文件和当前会话的分工：长期规则写入 `AGENTS.md` 等规则文件；本轮任务、临时优先级和阶段性要求留在当前会话。
- 强调输出命名：任务文件夹采用 `{YYYY-MM-DD}-{任务名}/`，正文、日报和其他产出物文件名应体现内容。
- 学习证据：画出个人课程项目目录图，并标注只读区、可写区、模板区和规则文件。

写作边界：

- 不把 `参考资料/` 中原始材料改写为输出。
- 不私自调整根目录 `大纲.md` 的章节结构。
- 不把临时任务要求写成长期项目规则。

### 2.6 环境验收、路径检查与常见排错

内容要点：

- 定义环境验收：用可复查命令和记录确认工具可用，而不是只说“已经安装”。
- 验收内容包括当前路径、Git、Git 用户名和邮箱、Node.js、npm、Opencode、VS Code 命令、conda、Python、Pandoc 和 Skills。
- 排错顺序先看路径，再看命令拼写和安装状态，再看权限、网络或 PATH。失败过程也要记录。
- 排错记录至少包含操作系统、当前路径、执行命令、完整报错、已尝试步骤和仍需确认事项。
- 强调不盲目重装、不随意管理员运行、不让 AI 自行更改系统级环境。
- 学习证据：提交“环境验收与排错记录”，至少包含一个通过项和一个待确认项。

写作边界：

- 不承诺所有学生路径一致。
- 不把一次命令失败解释成软件不可用。
- 不要求学生独立解决所有系统级问题，无法确认时标 `需人工确认`。

### 正文写作约束

- 正文必须先列使用材料清单，并说明本章大纲已先讨论和更新。
- 六个小节标题必须与根目录 `大纲.md` 保持一致。
- 正文不写成长安装手册；详细安装步骤可留给附录 A 或课堂说明。
- 不使用 `imagegen` 生成图；知识结构用 Mermaid、表格和提示词表达。

- 遇到学校机房配置、学生电脑差异、工具最新状态或真实报错案例不足时，标注 `需补证据` 或 `需人工确认`。
